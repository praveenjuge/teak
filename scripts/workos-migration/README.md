# WorkOS migration operations

Prepared tools; no real import, delta, repair, rollback or cutover has run from this workstream.

Use Bun with `--no-env-file`. Supply the approved deployment name and its exact WorkOS environment/client IDs. Also pass `--witness-email` and `--witness-external-id` from the controlled target witness snapshot (`none` means a null external ID). The backend supplies the configured witness ID; the CLI verifies its provider response before any source export. Resume requires unchanged witness pins. Supply its API key at runtime from the existing credential store; never paste it into a command, journal, report or repository. Source pages recheck environment/client/key fingerprint and require frozen Better Auth primary. New users keep the permanent Teak owner; no cards owner changes.

1. Run `import-users.ts --preflight` with a fresh private journal path. It produces an owner-only `<journal>.preflight.json` containing full normalized-email collisions and password-format counts. Gmail dots and plus aliases stay distinct. Resolve collisions by hand; never automatically merge owners. A clear duplicate preflight is not a full reconciliation or cutover gate.
2. Run `import-users.ts --dry-run` against that same pinned deployment. This reads source and provider data but creates no users, mappings, quarantine or journal checkpoints. The password conversion remains off unless the controlled-account proof permits `--hashes-proven`.
3. After **separate explicit import approval**, run with `--apply --approval-reference <recorded approval>`. Every write run first repeats the complete owner/provider collision preflight automatically; any later-page collision stops source export and provider changes. Apply runs write an owner-only collision report and at most twenty unresolved quarantine receipts; an existing receipt keeps subsequent runs blocked without duplicate writes. Read-only preflight never writes quarantine. Delta preflight permits a known owner’s previous email and deletion tombstone, while preserving all cross-owner and duplicate fences. The CLI then persists admission before its first provider mutation, then atomically checkpoints its owner-only journal after each 20-owner page commits. Each write invocation acquires a deployment-wide durable lease with its own holder and generation. Before a provider mutation, it persists the exact owner/source intent; mapping and checkpoints require the same lease. A safely acknowledged create can resume by permanent external ID. A process loss, timeout or unacknowledged response keeps the lease blocked; no timed expiry grants another invocation authority. Resume with `--resume` only after the previous invocation has released, using the same pins and hash-conversion setting.
4. After **separate delta/backfill approval**, use `--delta` with the completed journal. The watermark is the previous run's start, so changes during a scan are revisited. Verification is exact. Resumed initial imports refresh the current proven password too. Unsupported or unproven resumed/changed hashes stop the run instead of silently keeping an old password. Deletions do not recreate provider users. The final pause/drain and rollback workflows must establish a durable `quiesced` barrier with `quiesce-importer.ts`, then require `verifyQuiescence` with its exact private held receipt before changing auth flags. A ready query alone does not authorize a transition: it leaves a query-to-writer race. The held barrier prevents any importer from acquiring authority until an explicitly approved release. Unknown provider completion requires separate operator resolution; the tools do not clear it automatically. Do not flip authentication while any importer request is in flight.
5. Read a completed **audit** report from `workosReconciliationCensus:readiness`. Missing mappings, legacy coverage, duplicate identities, email/verification drift and every unresolved quarantine prevent zero. A completed repair is never zero proof. Perform the first full audit with an explicit operator-chosen event window; only then activate the inert daily audit schedule using the separately reviewed environment pins.

All real imports, deltas, repair activation and production cutover remain separate approvals. Prepared additive schema approval does not authorize these operations. The daily schedule permits audit only; no scheduled delta or repair is activated by these tools.

Rehearsal remains required: a throwaway Convex deployment, empty private R2 bucket and WorkOS environment with email disabled, no production Resend/Polar/R2/E2E secrets, neutralized jobs, own webhook endpoints. Validate isolation before restore. Prove migrated sign-in sees the same owner's cards; run delta, flip, rollback and flip again with controlled account shapes. Capture browser/network artifacts and exact run IDs. Existing merged code and hermetic tests are not runtime proof.

Rollback password policy is pending a separate decision: conservatively invalidate every mapped legacy password because the current provider payload does not expose a complete credential revision. The prepared proposal is in the encrypted migration-backup directory. The read-only rollback plan also exposes unavailable canonical profiles, email conflicts, verification downgrades and new owners without legacy accounts; each blocks a safe flip until resolved. Do not invalidate credentials or execute rollback without its explicit activation approval.

The clean shadow week, every-store live date plus three weeks, seven-day notice, at least 48-hour rollback window and later retirement/backup-retention gates remain elapsed calendar time. No waived native test is counted as passed.

Prepared Phase 5 operator controls:

- `quiesce-importer.ts --deployment <exact> --environment-id <exact> --client-id <exact> --receipt <private-path> --operation establish` is read-only unless `--apply --approval-reference <separate-approval>` is supplied. Establish requires account changes paused and signups frozen; active or uncertain importer intent cannot be displaced. The invocation receipt survives a lost response; use its `.held` receipt for `verify` and separately approved `release`. Preserve the held barrier across cutover/rollback failures.
- After a separately approved WorkOS-primary flip, `revoke-legacy.ts --deployment <exact> --receipt <confirmed-held-receipt>` verifies the barrier read-only. `--apply --approval-reference <separate-revocation-approval>` drains Better Auth sessions and OAuth access/refresh pairs in bounded batches, proving completion with an empty page for both models. It retains account writes paused and the barrier held; it never flips authentication or unpauses. Completion evidence is private and append-only.
- Full transition automation is incomplete: final reconciliation and phase-boundary backup evidence, legacy auth ingress drain, lifecycle rollback application, and the calendar/runtime gates must still be satisfied. This command is step 5 preparation, not cutover authorization. Rollback password policy still requires its separate decision and writer.
