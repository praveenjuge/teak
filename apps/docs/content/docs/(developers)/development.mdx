**Prerequisites:** Git plus Bun and Node.js at the versions pinned in `package.json` (`packageManager` and `engines.node`). Setup validates both and refuses to run on the wrong toolchain.

## Quick Start (local)

<Steps>
  <Step title="Clone the repository">
    ```bash
    git clone https://github.com/praveenjuge/teak.git
    ```
  </Step>
  <Step title="Move into the project">
    ```bash
    cd teak
    ```
  </Step>
  <Step title="Start the app">
    ```bash
    bunx convex login
    bun run dev
    ```

    The first run installs dependencies and writes the local env files. It then starts the web app against Teak's shared Convex development deployment, signed in through WorkOS staging, and creates a sign-in account for this checkout seeded with sample cards. Uploads, previews, AI metadata and the other backend features work as they do on that deployment. When it's ready it prints the URL and the sign-in. It needs access to the Teak Convex project; without it, see [Without access to the development deployment](#without-access-to-the-development-deployment).
  </Step>
  <Step title="Check the setup">
    ```bash
    bun run doctor
    ```
  </Step>
</Steps>

## Access Points

- Web app: http://localhost:3000 (each git worktree gets its own ports; `bun run dev --status` prints them)
- Docs (proxies `/api` and `/mcp` to the development deployment): http://localhost:3001
- Mobile: Expo Go or a simulator; Mac app and Safari extension: Xcode

See the repository README for the monorepo layout.

## Core Commands

```bash
bun run dev              # Set up, then start the web app on the development deployment, seeded
bun run dev --push       # Same, and push this checkout's backend code
bun run dev --status     # This checkout's ports, URLs and sign-in
bun run dev --stop       # Stop this checkout's stack
bun run setup            # Set up only (--target for other surfaces)
bun run doctor           # Validate the environment (--json --target for agents)
bun run dev --all        # All services
bun run smoke:web        # Headless sign-in check against the running stack
bun run audit:env        # Environment contract + local dotenv audit

bun run dev convex       # Convex backend only
bun run dev mobile       # Expo mobile
bun run dev extension    # Chrome extension
open apps/mac/teak-mac.xcodeproj # Mac app and Safari extension
bun run dev raycast      # Raycast extension
bun run dev docs         # Docs site

bun run build            # Production build (all)
bun run build:extension  # Package Chrome extension
bun run build:raycast    # Build Raycast extension

bun run lint && bun run typecheck
bun run test             # Unit tests (turbo; test:unit / test:edge for Convex splits)
bun run verify           # typecheck + lint + test (affected)

bun run check            # Quality report (Ultracite)
bun run fix              # Auto-fix issues

bun run pre-commit       # Pre-commit checks
bun run publish:raycast  # Publish to Raycast store
bun run clean            # Clear Turborepo caches
```

## Supported Targets and Limitations

`bun run setup --target <name>` provisions one surface. Every surface uses the
shared development deployment and its WorkOS staging environment; setup reads
the WorkOS client ID and API key from the deployment, so nothing is copied by
hand.

| Target | Needs | Limitations |
| --- | --- | --- |
| `web` | Access to the development deployment | Only one checkout at a time pushes backend code (see below) |
| `docs`, `cli` | Nothing beyond install | No Convex provisioning |
| `extension` | Access to the development deployment | Env files derive `VITE_*` aliases automatically |
| `mobile-simulator` | Access to the development deployment | Signs in through WorkOS staging |
| `mobile-device` | Access to the development deployment, LAN | The host must be LAN-reachable for the Expo dev server |
| `files-worker` | `bun run sync:cloudflare-dev` afterwards | Worker secrets are owned by the sync command, not setup |

Each linked git worktree gets its own web ports, so several worktrees run at
once against the same development deployment. Because they share its code,
only the checkout holding the push lease runs `convex dev`; the others run the
web app against the live code. `bun run dev --push` takes the lease over.
iOS simulators, device builds, the Mac app, Xcode, and Safari stay on macOS.

### Without access to the development deployment

Set up your own deployment as in [Self-Hosting](/docs/self-hosting). The E2E
suite (`bun run --cwd packages/tests e2e`) needs no credentials; it runs its own
throwaway stack for tests only (`packages/tests/README.md`).

## Reporting Setup Problems

Paste the redacted JSON report with your issue. It contains check names and
remediations but never secret values:

```bash
bun run doctor --target web --json
```

## Setup Checklist

### Convex and sign-in

Teak signs in with WorkOS AuthKit everywhere: production, local development, CI, and self-hosted deployments. There is no other provider and no switch.

Locally, the web app signs in through the WorkOS staging environment that the development deployment uses, never production. Setup reads `WORKOS_CLIENT_ID` and `WORKOS_API_KEY` from the deployment and writes them into `apps/web/.env.local`, alongside `NEXT_PUBLIC_WORKOS_REDIRECT_URI` (the app origin plus `/callback`) and a generated `WORKOS_COOKIE_PASSWORD`. It refuses production keys, and it stops if a shell export disagrees with the deployment. The E2E suite signs in through the local WorkOS emulator instead.

`convex.json` declares the AuthKit redirect URIs, CORS origins, and homepage URL, including every worktree web port. For cloud development deployments, Convex applies them to the deployment's WorkOS environment. The sign-out redirect, JWT template, and webhook are not in `convex.json`; set them once per environment as in [Set up WorkOS](/docs/self-hosting#set-up-workos), which also lists the [WorkOS CLI](/docs/self-hosting#use-the-workos-cli) commands for them.

The CLI, browser extensions, Mac app, Raycast, and MCP sign in through WorkOS Connect. To sign them in against your development deployment, configure Connect and set `WORKOS_AUTHKIT_DOMAIN` and the `WORKOS_CONNECT_*_CLIENT_ID` values as in [Connect](/docs/self-hosting#connect-cli-browser-extensions-mac-app-raycast-and-mcp).

`bun run doctor` fails until the deployment and the web app both have the client ID and API key, checks that the client, key, cookie password, and callback fit together, and warns about development settings the deployment's owner hasn't set yet.

Social sign-in, such as Google or Apple, is configured inside WorkOS, not in Teak.

### Public API and MCP

The public REST API, MCP endpoint, discovery routes, OpenAPI spec, and SDK live in `packages/convex`. The development deployment serves the HTTP routes; push this checkout's backend first if you changed them, then use the docs dev proxy for local API and MCP URLs.

Example:

```bash
bun run dev convex
```

The docs dev server proxies `/api`, `/mcp`, and OAuth protected-resource metadata to the Convex dev deployment. That gives local docs, examples, and smoke tests the same path shape as production: `/api/v1` and `/mcp`.

Native OAuth clients sign in through WorkOS Connect and disconnect with `POST /v1/oauth/disconnect` (see [Disconnect an OAuth connection](/docs/api#disconnect-an-oauth-connection)).

### MCP Registry

The repo includes `server.json` for the MCP registry under the `com.teakvault/mcp` namespace. Publishing is manual because the namespace requires DNS verification for `teakvault.com`:

```bash
npm install -g mcp-publisher
mcp-publisher login dns
mcp-publisher publish
```

Follow the CLI prompt to add the DNS TXT record, then publish once verification passes.

### Environment Variables

See **[Self-Hosting → Environment settings](/docs/self-hosting#detailed-environment-reference)** for every env var required across web, mobile, extension, and the Convex backend.

Development URLs on the deployment: `TEAK_DEV_APP_URL` (default: `http://localhost:3000`), `TEAK_DEV_API_URL` (default: the development deployment's site URL), `TEAK_DEV_DOCS_URL` (default: `http://localhost:3001`).
