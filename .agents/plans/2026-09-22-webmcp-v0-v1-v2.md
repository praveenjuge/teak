## Goal

Ship WebMCP v0 hardening, v1 curated writes, and v2 composed reads plus an eval harness for the Teak web app in a single pull request to `main`: fully working locally, covered by unit and e2e tests, with a proof bundle, followed by review handling, merge, post-merge verification, and a local `main` sync.

## Success Criteria

- The two existing read-only tools carry spec annotations; three v1 write tools and one v2 composed tool register for signed-in sessions only.
- Every tool has unit coverage (happy path, invalid input, shaping) and e2e coverage through the mock `modelContext`; the full local suite is green.
- A proof bundle is presented: typecheck, lint, unit, e2e (un-skipped), eval script, build, and a manual Chrome-flag check.
- One PR is merged to `main` with clean required checks and no unresolved relevant review feedback.
- Post-merge `main` is green, the production live check passes, and the local repo is synced to `origin/main`.

- Backend reuse targets (verified signatures): `createCard` (`packages/convex/card/createCard.ts:248`, args content/type/url/fileKey/thumbnailKey/tags/notes/metadata/colors, session-required) and `updateCardField` (`packages/convex/card/updateCard.ts:377`, `cardId`/`field`/`value`/`tagToRemove`, session-required, returns null). No Greptile config exists in the repo (a GitHub App would only be visible on the PR itself). `apps/web/vercel.json` deploys only `main` (no PR previews). `backend-deploy.yml` triggers on `main` pushes but is path-filtered to Convex/worker paths, so web-only changes do not trigger it. Production base URL evidence: `api-smoke.yml` defaults to `https://teakvault.com`.
- Spec facts (inspected this run): `ModelContextTool` takes required `name`/`description`/`execute` plus optional `title`/`inputSchema`/`annotations`; `ToolAnnotations` is four booleans defaulting to false (`readOnlyHint`, `untrustedContentHint`, `consequentialHint`, `debugging`). The `tools` Permissions-Policy feature defaults to `self`. Chrome guidance: `readOnlyHint` on non-mutating tools, `untrustedContentHint` when a tool returns UGC, `consequentialHint` for significant actions so the agent or browser can confirm. Local development uses `about:flags#enable-webmcp-testing`; origin trials are live in Chrome 149 and Edge 150.

## Constraints And Non-goals

- Web-only diff: no `packages/convex` changes, so no schema-change approval is needed (`packages/convex/AGENTS.md`). Server-side auth, ownership, quota, and validation stay the source of truth.
- No `delete` / `restore` / `permanentDeleteCard` tools in v1 (destructive; later phase).
- No file-based create types in v1 (image/video/audio/document/palette need upload flows).
- No multimodal I/O, `outputSchema`, user elicitation, streaming, service-worker registration, or skills packaging (spec open questions, no stable API).
- Single PR to `main`, per the request. Never bypass git hooks (`--no-verify` is forbidden). No history rewrites: fold `main` into the branch with a merge commit if it moves, never rebase pushed work.
- E2E mutations are confined to the e2e user with unique content per run.

## Key Decisions

1. One PR for v0+v1+v2 (user instruction). Rejected stacked PRs: the phases share the same two provider files and the e2e mock, so splitting buys review overhead without isolation.
2. v1 stays web-only with no idempotency-key backend change (that would need schema approval). Double-submit risk is mitigated with `consequentialHint`, read-back confirmation, and a documented follow-up for server-side idempotency.
3. v1 tools are exactly `teak_create_card` (types text/quote/link only), `teak_update_tags` (add/remove over user tags), and `teak_set_favorite` (explicit boolean). Each maps 1:1 to an audited mutation; destructive and file-based operations are excluded by Constraints.
4. `teak_update_tags` does client-side read-merge-write (fetch card, merge, replace) because the server `tags` case replaces the whole array. Exact-match merging; documented in the tool description.
5. Annotations: `readOnlyHint` + `untrustedContentHint` on all read tools (card content/notes are UGC); `consequentialHint` on all write tools. Source: spec IDL plus Chrome secure-tools guidance.
6. Same-origin only; no `exposedTo` allowlist. Chrome guidance limits write-capable tools to trusted origins, and Teak has no embed use case.
7. Eval harness is repo-local (multi-tool gold-scenario script, deterministic fakes, no backend) rather than an external eval CLI: zero new dependencies and it runs anywhere `bun` runs.
8. Telemetry is dev-only console logging plus counters on the existing non-prod `window.__teakWebmcp` debug handle. Rejected Sentry events: agent-call volume would be noise; production telemetry is a follow-up.
9. Declarative coverage stays at the existing search form; no declarative create form in v1 (the declarative spec section is still TODO and autosubmit semantics for writes are unproven).

## Recommended Approach

Extend the existing provider in place (`webmcp.ts` + `WebMcpTools.tsx`), following its established patterns (static descriptions, `additionalProperties: false` schemas, fail-closed `normalize*` functions, `WebMcpQueryDeps` injection, `AbortController` cleanup). Mirror the existing unit-test `setup()` and e2e mock-modelContext patterns for every new tool. Verify locally in layers (unit, e2e un-skipped, eval script, build, manual Chrome flag check), assemble the proof bundle, then run one PR through review to merge and verify post-merge.

## Risks / Rollback

- Draft-spec drift: the API is a 2026-09-17 Community Group draft, not a standard. Mitigation: annotations are additive optional fields, `getModelContext` already probes both entry points, and registration fails soft. Risk is contained to the two provider files.
- Origin-trial token vs flag: local proof uses the documented testing flag, avoiding trial-token enrollment; production exposure inherits whatever trial state the browser has.
- E2E environment: Convex dev backend plus e2e creds are required; `playwright.config.ts` boots the stack and `workers: 1` limits flakiness. Baseline in Phase 0 exposes environment issues before they can be mistaken for regressions.
- Write-tool misuse: tools are same-origin, session-bound, reuse audited mutations, and carry `consequentialHint`; destructive operations are excluded from scope.
- Rollback: revert the single PR. The feature is additive and registration fails soft, so revert risk is minimal and no data migration is involved.
